# AI-assisted development log

OpenAI Codex was the primary coding agent for both prototypes. The milestones
record the user’s direction, the agent’s contribution, and what was verified.

## Auth0 SSO

| Milestone | Direction and agent contribution | Review and verification |
| --- | --- | --- |
| Plan and Drupal setup | The user supplied the module plan and asked Codex to review the Drupal workspace and implement the prototype. Codex inspected the Composer and DDEV setup, upstream module source, Drupal routing, and the API contracts. | The user directed Codex to follow the module plan and keep the repository and README ready for interviewer review. |
| Authentication and first login | Codex initially implemented against the Drupal OIDC Client module. After the user requested OpenID Connect and clarified the External Auth boundary, Codex checked Composer and switched to `openid_connect`. It verified upstream hooks and selected the 3.x revision with strict ID-token verification. | The custom module declares only OpenID Connect and calls its hooks and destination API. The kernel test checks first-login account creation, repeated login with the same account, role synchronization, redirect priority, and revocation using a token-validator fixture. |
| Dashboards and access | Codex implemented two Drupal routes with core role checks, shared public-data caching, and separate Guzzle clients. Each response renders the current user’s identity. | Unit and browser tests cover role checks, escaped remote data, cached responses, and upstream failure. |
| Local recovery | The user reported the missing `openid_connect.session` service. Codex inspected the local extension registry, backed it up, removed stale registrations, and enabled the two required modules. | Drupal bootstrapped again. The home and login pages returned HTTP 200 and the anonymous member dashboard returned HTTP 403. |
| Final brief and external services | After receiving the full brief, Codex replaced the initial CountryInfo URL with the specified Beeceptor endpoint. It checked the WSDL for the request namespace and action, and used the namespace returned by the mock for response parsing. | Calls through Drupal's live service clients returned Leanne Graham's sample record and 246 country entries. The initial live Auth0 run awaited tenant configuration. |
| Submission evidence | Codex used Chromium to capture both dashboards and direct-access denials with local Drupal demo accounts. It updated the README and reviewed module plan for the interviewer. | The browser verified both dashboards returned HTTP 200 with live API data, cross-role requests returned HTTP 403, and both anonymous requests returned HTTP 403. The full Drupal suite passed 12 tests with 66 assertions. |
| Live Auth0 and cache validation | The user supplied tenant settings and diagnosed a missing role claim with Codex. The Post Login flow screenshot showed no attached Action. The user attached the Action, and Codex added configurable role aliases, shared public-data caching, and stricter HTTP response checks. | Live member sign-in mapped the role and opened the REST dashboard. The opposite route returned 403. Live logout cleared both sessions. DDEV requests confirmed both external APIs, and the second SOAP read used the shared cache. Local settings hold the Auth0 secret outside exportable Drupal configuration. |
| Assessment audit | The user asked Codex to check the full brief against the current workspace and GitHub remote. | Verified one linked member and one linked exhibitor in Drupal. The fresh exhibitor redirect and logout replay and live revocation are still open. The audit recorded the remaining validation and publication steps. |
| Login and cache review | The user asked to redirect local dashboard users after sign-in, reviewed the controller’s cache changes, and chose to place the Auth0 button below Drupal’s login form. Codex consolidated the role-based redirect and kept the public API response cache separate from the personalized dashboard. | Verified the local member redirect in a browser and preserved 403 for the exhibitor route. A fresh-install functional test checked the Auth0 button placement. The suite passed 12 tests with 86 assertions. |
| miniOrange evaluation | The user selected miniOrange after reviewing the Specbee SAML walkthrough. Codex inspected the Drupal package, added a scoped SAML Action, and updated the cutover plan. | miniOrange 3.2.1 installed on an isolated Drupal 11 site. The public edition supports a default role for new users, and the planned cutover needs the licensed edition for assertion-based roles and single logout. |
| Interview handoff | The user requested a simplified README, an architecture diagram, and updated planning and AI log deliverables. Codex aligned the documentation with the verified OIDC demo and the pending SAML cutover. | The repository records live member login and logout, both live APIs, screenshots from local demo accounts, and the remaining live exhibitor and role-revocation checks. |
| Assessment cleanup | The user asked to keep the SAML Action and remove unused modules and files. Codex removed the inactive miniOrange dependency and kept the verified OpenID Connect runtime. | Composer reported no advisories after removal. The supplied credentials were rejected for both Auth0 accounts on the latest replay. |
| Two-account live validation | The user corrected the test password. Codex repeated both Auth0 sign-ins in separate browser sessions. | Each account reached its assigned dashboard with HTTP 200. The opposite dashboard returned 403. Auth0 logout returned both accounts to Drupal and both dashboard routes then returned 403. |
